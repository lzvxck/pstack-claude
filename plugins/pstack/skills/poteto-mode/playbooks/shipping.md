### Shipping

**You own the verdict. Verify each PR independently, report only the verified run merge-ready, and never merge.** For "land the stack", "ship it", "is this safe to merge", or the second half of a stack that **Babysit** already drove to green.

This is the half after `playbooks/babysit.md`. Babysit makes a stack mergeable. Shipping decides what is actually safe to merge and hands the user that decision as evidence. Green is not safe, and the gap between those two words is where this playbook lives. Merging is always the user's click; nothing in this playbook merges, enables auto-merge, or arms anything.

1. **Verify every PR independently before calling anything merge-ready.** One subagent per PR, not batched, each in its own worktree at the PR head, each exercising the real surface (`control-ui` or `control-cli` from `cursor-team-kit` as the change demands) against parent versus head. Each returns `PASS`, `PASS+NOTES` or `FAIL` and posts that verdict on its own PR so the record outlives the chat. Safe means a verdict from an agent that did not write the code. CI green is not a verdict, and an approving bot review is not a verdict.
2. **Report merge-ready only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without a passing verdict, where both `PASS` and `PASS+NOTES` pass. A verified PR sitting above an unverified one is not merge-ready, because merging it would pull the gap in underneath it. Report the ceiling as a PR number and say what breaks the chain.
3. **Re-check that the verdicts still describe the code.** A rebase rewrites every SHA above it and silently invalidates every verdict without touching a single check. Compare `git patch-id` at the verdict SHA against the current head before trusting an older verdict, and re-verify anything that actually drifted. Twenty-one verdicts went stale this way in one run with no signal at all.
4. **Never merge and never enable auto-merge.** No `gh pr merge`, no `--auto`, no merge queue arming. If a previous agent enabled auto-merge, disarm with `gh pr merge <n> --disable-auto` and confirm the field is back off. On a chained stack, auto-merge is doubly dangerous: children target unprotected parent branches that already read `CLEAN`, so GitHub would merge children into parents immediately and collapse the chain into itself.
5. **Hand the user a merge order, not just a verdict list.** The verified run merges bottom-up. For a chained stack, name each PR in order, and remind that after each merge the next PR's base needs retargeting to trunk (`gh pr edit <n> --base main`) if GitHub does not retarget it automatically. Those retargets are the user's or the owner's, not yours; shipping does not mutate topology.
6. **If asked to watch the user's drain, watch, do not drive.** Arm the watcher in queued mode over the verified run and hold it as the event wake, re-armed after any verdict you act on, until `COMPLETE` at the ceiling. `ADVANCE` is progress, not termination. Report each merge and the new ceiling. If the queue stalls, diagnose before mutating, because a stalled queue and a broken stack look identical from the outside. Without that explicit ask, stop after the report.
7. **Stop at the ceiling.** Report the verified run, the next unverified PR, and what verifying it would take. Extending the run is a new pass through step 1, not a judgment call you make at 3am.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, the bottom-up merge order for the user, and what the next gap needs.
